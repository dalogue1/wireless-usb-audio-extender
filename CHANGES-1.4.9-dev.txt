Wireless USB Audio Extender 1.4.9-dev  (radio protocol v22: update both boards)

- PDM microphones on the XIAO remote, found automatically at start-up (no setting):
  1. a USB device in the OTG adapter (D+ or D- pulled high): the USB audio adapter, as before;
  2. else the External PDM Microphone board (IM73D122) in the OTG adapter's USB-A socket:
     PDM clock on USB D- (GPIO19, weakest drive), data on USB D+ (GPIO20); the USB-Serial-JTAG
     pad and its D+ pull-up are released first, and the USB host is never started;
  3. else a PDM microphone wired to D3 (clock, GPIO4) / D2 (data, GPIO3), checked before
     the Sense so a mic wired to a Sense board wins;
  4. else the XIAO ESP32-S3 Sense's built-in microphone (clock GPIO42, data GPIO41);
  5. else the USB host starts and waits for an adapter (as before).
  Decided once per start: to change microphones, restart the remote. A PDM microphone is
  microphone mode only (mode reason "remote uses a PDM microphone"). The remote's log says what
  it found ("microphone: ..."), with what each data line did when nothing was found.
- PDM capture (AudioExtender_Remote/PdmMic.h, was BuiltInMic.h) is shared by every PDM mic,
  AtomS3U included. The slot (SELECT pin; JP1 on the board) is now picked by variance, not
  energy, so an idle slot held at one level can't win. mic_level is the PDM digital gain
  (0-100 = 0 to +30 dB, default +30 dB), as on the AtomS3U.
- No-signal check for PDM mics: a data line that stops (board unplugged) freezes the samples
  at one value; that now counts as no signal (20 s), like silence from a USB adapter.
- status.txt names the microphone and its PDM slot; adapter.txt describes the PDM microphone
  (e.g. "External PDM Microphone", IM73D122, 48 kHz, left slot, JP1, gain) instead of
  adapter descriptors. New status fields micSource / micSlot (protocol v22).
- Stereo USB microphones and adapters (48 kHz stereo, 192-200 byte packets), e.g. the Blue
  Yeti: refused before with "could not claim the audio interface". The core's USB host is
  built with its FIFO biased towards periodic OUT, which caps IN packets at 128 bytes. The
  remote now sets its own FIFO split (UsbMic.cpp libTaskFn): IN packets up to 340 bytes,
  speaker packets up to 352 bytes. The left channel of a stereo microphone is used.
  A packet size the USB host still can't take is reported as "packets too large for the
  USB host (N bytes)"; the log gives the ESP-IDF error of any failed claim.

Also in this build (from 1.4.8-dev):
- New config.txt settings: lowpass = off | on, lowpass_hz = 12000 (2000-20000 Hz).
  An 8th-order Butterworth low-pass (48 dB/octave) at the remote, after the high-pass:
  removes hiss above the cut-off, e.g. the AtomS3U built-in mic's hiss above ~14 kHz.
  Off by default. status.txt, the log, the settings line and the noise graph show it.
  Works on every remote (USB adapter or AtomS3U built-in mic).
- AtomS3U built-in mic: a fixed notch removes a tone the mic picks up from the chip
  itself at exactly 48 kHz / 7 = 6857 Hz (strong at cpu_mhz 160, at times at 240).
  Always on, built-in mic only; USB adapters are not touched.
- Docs: noise-filter.md has a new "low-pass filter" section; atoms3u.md explains the
  6857 Hz tone; configuration.md, noise-filter-technical.md, building.md and the
  example config.txt / status.txt updated.

Also in this build (from 1.4.7-dev):
- config.txt setting audio_compression = auto | none | low | high (both boards): the
  microphone audio format independently of the radio rate. auto (the default) follows
  distance: near = none, normal = low, far = high.
- The remote no longer restarts itself for a weak signal: the "stuck transmitter"
  restart needs the radio silent for 2 s or nothing acknowledged for 5 s.
- At most 8 audio packets (96 ms) wait in the remote's radio; newer audio is skipped
  (counted as lost) rather than queueing audio that would arrive too late.
- Drive opening waits up to 8 s for the remote's temperature and logs why if none came.
- Remote chip temperature as the drive opens: never worked since it was added in 1.4.3.
  The packet check (wlink::check in LinkProtocol.h) had no case for kTempRequest, so the
  remote dropped every request ("asked 8 times, no answer in 8 s" in status.txt, 1.4.6+).
  Fixed; a host test now checks that every packet type is accepted.
  Second fault behind it: the remote cleared its new reading at once (the age was taken from
  the loop's start time, older than the reading, and wrapped round), so the local board never
  saw it and kept asking. Ages now come from millis().
